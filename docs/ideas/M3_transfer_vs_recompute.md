# M3 传 KV、重算还是留下

- 类别：方法（迁移方式）
- 状态：草案
- 分支：`idea/M3-transfer-recompute`
- 负责人：
- 依赖：B1（对照）

## 一句话假设

现在迁移只有「传整段 KV」一种方式。如果允许只传 token、到目标星重新算 prefill，链路紧张时用算力换带宽，超时中断会明显减少，在带宽很紧的 E★ 场景里收益最大。

## 机制

量级先算清楚。按 `base_ring_s1.yaml` 的模型参数，每个 token 的 KV 是 32 层 × 8 头 × 128 维 × 2 字节 × 2（K 和 V）= 128 KiB。长请求输入 8000 token，KV 约 1 GiB：

- **传 KV**：10 Gbps 独占约 0.9 秒；E★ 的 0.5 Gbps 下约 17 秒，几条流一叠就到 30 秒超时线。
- **重算**：只传 token id，几十 KB，链路几乎不占；代价是目标星要把整段序列重新 prefill 一遍。目标星本来就是亮星、有空闲算力，这正是「算力和链路同时在变」的取舍点。
- **留下**：不占链路也不占目标星，代价是在慢星上继续慢慢算。

每次决定迁移时，三种方式各估一个「剩余输出全部生成完的预计时间」，选最小的：

```text
传 KV：  T_transfer(当前链路状态) + 剩余 token × 目的星每 token 耗时
重算：    T_prefill(序列长度, 目的星时钟) + 剩余 token × 目的星每 token 耗时
留下：    剩余 token × 源星每 token 耗时
```

进阶版本（参考 Pallas）：前缀在目标星重算，同时源星继续生成，新生成部分的 KV 边算边传，两边都准备好再切换。第一版先不做。

## 前置条件

引擎目前完全不建模 prefill 耗时，也没有「在目标星重算」这个动作。要在本分支加：

- 一个新的迁移类型：传输量 = token 数 × 4 字节，到达后目标星先占用一段 prefill 时间才开始生成。
- prefill 耗时模型：先用 `gpu` 里已有的参数折算，单独写一条 ADR 说明假设。

这一条会改引擎，冲突风险比其他思路高。改动限定在新增迁移类型，不改现有传 KV 的路径。

## 相关工作

- Pallas（arXiv 2608.16477）：前缀重算加后缀流式传输的混合迁移。它只处理单条迁移，没有多流争用。
- SpotServe（ASPLOS'24）：按 token 粒度提交进度，迁移时复用 KV，避免从头重算。
- CacheGen（SIGCOMM'24）：压缩 KV 后再走网络传。可以作为第四种方式的参考，第一版不做。

## 实验设计

- 场景：E★ 瓶颈边（主）、四星环、跨轨网格；E★ 上扫 `link_gbps ∈ {0.5, 1, 2, 10}`
- 对照组：首次分配、无消耗迁移、随机迁移、贪心加准入（`B1`）；外加两个消融：只传 KV、只重算
- 种子：1–5

## 成功判据

E★ 上超时中断比贪心加准入少一半以上，有效吞吐高一个标准差以上；扫带宽时能看到选择方式随带宽切换，带宽紧时偏重算，宽时偏传 KV。

## 放弃判据

在合理参数下某一种方式总是最优（比如重算永远赢），那就只是个参数结论，不是策略。写成一句话结论并入别的思路，不单独推进。
