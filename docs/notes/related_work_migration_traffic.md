# 迁移流量感知的算力调度：相关工作

整理日期：2026-11-04。和 `multi_flow_throughput_traditional.md` 互补：那份讲传统网络怎么处理多流争用，这份讲「流量是迁移决策自己产生的」以及「算力在时间和空间上变化」这两块。2026 年的预印本目前只读了摘要，写进论文前要精读。

## 我们的问题和集合通信差在哪

集合通信（all-reduce 等）的流量矩阵由算法固定，调度只能决定什么时候传、走哪条路。我们的流量矩阵是调度器自己生成的：迁不迁、迁谁、迁去哪，决定了链路上有哪些流。所以决策变量比集合通信多一层「要不要产生这条流」。

两种变化：

- **时间上**：星什么时候变暗。地影可以按轨道预测；突发过热不能。
- **空间上**：哪几颗星同时变暗。地影沿轨道依次扫过，变暗的星是挨着的，所有请求都想往亮的那一侧逃，迁移流量在空间上是相关的、在时间上是突发的。

## 按支撑点分组

### 一、迁移流量会造成拥塞，是真问题（LLM 服务）

| 工作 | 做了什么 | 和我们的差别 |
|---|---|---|
| [Connex（SIGCOMM'26）](https://yanyinglin.github.io/assets/pdf/Connex-Sigcomm26.pdf) | 把「迁移流量引起拥塞」列为弹性 LLM 服务的三大挑战之一（原文 C3），用通信层反压解决 | 在通信层做，不在调度层决定要不要迁 |
| [Vesta（arXiv 2610.14686）](https://arxiv.org/abs/2610.14686) | 选执行位置时把 KV 传输代价和排队外部性一起算；集群拥塞时少迁 | 数据中心，算力不随时间变 |
| [ARK（arXiv 2610.41160）](https://arxiv.org/abs/2610.41160) | prefill 和 decode 分离部署时，KV 传输是持续很久的大流，用路径预留避免哈希撞车 | 只管走哪条路，迁移需求是给定的 |
| [HICS（HPEC'26）](https://ieee-hpec.org/wp-content/uploads/2026/09/145.pdf) | 联合选网络通道、传输方式、放置和路径，缓解 KV 迁移造成的拥塞 | 数据中心异构互联，没有算力变化 |
| Llumnix（OSDI'24） | LLM 服务里的 KV 热迁移，用于负载均衡 | 默认数据中心带宽充足 |

### 二、算力变化可预测时提前迁

| 工作 | 做了什么 | 和我们的差别 |
|---|---|---|
| [Pallas（arXiv 2608.16477）](https://arxiv.org/html/2608.16477) | 基站切换前按移动性预测提前准备：前缀在目标端重算，后缀 KV 边算边传；在线挑提前多久开始 | 只处理单条迁移，没有多流争用；最接近 `M2`、`M3` |
| [SpotServe（ASPLOS'24）](https://arxiv.org/html/2311.15566) | 抢占式实例有约 30 秒宽限期；用二分图匹配规划迁移，让通信代价最小；按 token 粒度提交进度 | 抢占是整台消失，不是变慢；数据中心网络 |
| [CASSINI（NSDI'24）](https://www.usenix.org/conference/nsdi24/presentation/rajasekaran) | 训练任务放置加时间偏移，让共享链路上的通信阶段交错，完成时间最多改善 1.6 倍（平均）和 2.5 倍（尾部） | 流量是周期性训练通信，不是迁移产生的；空间加时间的思路最接近 `M2` |

### 三、卫星侧：日照驱动的迁移有人做，但没碰迁移之间的争用

| 工作 | 做了什么 | 和我们的差别 |
|---|---|---|
| [Phoenix（arXiv 2407.07337）](https://arxiv.org/html/2407.07337) | 日照感知调度，把任务卸载到始终被照亮的星或地面，电池消耗最多降 54.8% | 目标是省电池；通用任务，不是在线推理 |
| [SPTD（ICPADS'25）](https://doi.org/10.1109/icpads67057.2025.11322963) | 地影期间把任务迁到被照亮的星；混合整数非线性规划建模，评分里用到星间链路带宽 | **卫星侧最需要区分的一篇**。目标是能耗；摘要看不出有没有建模多条迁移之间的争用，要精读 |
| [SkyMemory（CCNC'26）](https://arxiv.org/html/2505.14427) | 在 LEO 星座里分布式存 KV 分块，可见性变化时迁移分块 | 用来加速 prefill 缓存命中，不是迁走正在生成的请求 |
| [GreenRP（Electronics 2025）](https://www.mdpi.com/2079-9292/14/15/3075) | 考虑电池放电深度的任务卸载和路由 | 关注电池寿命，不是推理延迟 |
| Denby & Lucia，Orbital Edge Computing（ASPLOS'20） | 能量受限的星上计算 | 背景引用 |

### 四、经典支撑

- Meng 等，Traffic-aware VM placement（INFOCOM 2010）：按流量矩阵放虚拟机。流量矩阵是给定的。
- Varys（SIGCOMM'14）、Sincronia（SIGCOMM'18）：一组流以最慢的那条为准，按组调度。对应「一次迁移要整段 KV 传完才生效」。
- PDQ（SIGCOMM'12）、pFabric（SIGCOMM'13）：争用时公平分带宽对截止达成率不是最优。
- 更多见 `multi_flow_throughput_traditional.md`。

| 工作 | 迁移流量互相争用 | 算力变化可预测 | 空间上相关的热点 | 迁还是留 | LLM 的 KV |
|---|---|---|---|---|---|
| CASSINI | 是（训练流量） | 周期性 | 否 | 否 | 否 |

## 和并行思路的对应

| 思路 | 主要借鉴 |
|---|---|
| `S1` 地影波 | Phoenix、SPTD 的物理背景 |
| `B1` 贪心不看链路 | Llumnix 的负载驱动迁移；PDQ / Varys 的截止准入 |
| `M1` 路径重叠选目的地 | Meng 等；Vesta |
| `M2` 提前迁、错峰迁 | CASSINI；Pallas；SpotServe |
| `M3` 传 KV、重算还是留下 | Pallas；SpotServe；CacheGen（SIGCOMM'24） |
| `M4` 截止感知的准入与排序 | Varys；PDQ；pFabric；Sincronia |
