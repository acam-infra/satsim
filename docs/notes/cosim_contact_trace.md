# 协同仿真实验: 轨道时变拓扑下的在轨推理调度

引擎说明见 `docs/adr/0005-cosim-contact-trace.md`; 复现命令在文末。

## 问题

orbitsim 的几何分析 (research_out/README.md) 给出两个判断:
地影可预知, 星历放置就能躲开; 遥感星 → 算力星的单链路接触只有分钟级, 可能是更真实的强迫迁移来源。
这两个判断都只看了几何, 没有跑过请求。协同仿真把 orbitsim 的接触轨迹接进 satsim 的网络与推理
模型, 问: 在真实时变拓扑上, 运行中迁移比"用星历放置"多买到多少?

## 场景

| 场景 | 算力星 | 链路 | 轨迹统计 (2 h) |
|---|---|---|---|
| `cosim_coop_w53_v1` | Walker 53° 4×10, 550 km | 面内环常连; 跨面 +Grid ≤ 5000 km 时在线; RS 一个激光终端, 保持当前算力星直到出 4000 km | 跨面接触中位 17 min; RS 接触中位 4.7 min, 每星每小时切换 11.8 次; 算力星 32% 时间在地影 |
| `cosim_coop_sso2_v1` | SOW S-SSO2: 4 簇 × 4 星, LTAN 10:30 / 13:30 | 簇内固定; 簇间 ≤ 5000 km (实测从不达到) | RS 接触中位 5.1 min, 每星每小时 1 次; 36% 时间在地影 |

两个场景都是 3 颗遥感星 (RS-1030 / RS-1330 / RS-SAR), 春分, 2 小时, 5 s 采样。
负载: 每颗 RS 泊松到达, 35% 长任务 (6k–18k token, 上传 500 MB), 截止时间 = 到达 + 2× 单独在亮星上的解码时间。

## 结果 (3 种子均值)

**Walker 53° 4×10, 每 RS 45 请求/分钟 (约 12k 请求)**

| 策略 | 长任务达标 | 全部达标 | 影内解码占比 | 迁移次数 | 迁移中止 |
|---|---|---|---|---|---|
| greedy | 95.9% | 98.4% | 2.4% | 0 | 0 |
| reactive | 97.1% | 98.8% | 0.2% | 232 | 0 |
| ephemeris | 99.3% | 99.7% | 1.8% | 0 | 0 |
| contact_aware | 99.9% | 100.0% | 1.6% | 304 | 0 |

**S-SSO2 4×4, 每 RS 4 请求/分钟**

| 策略 | 长任务达标 | 长任务交付 p90 | 影内解码占比 | 迁移次数 |
|---|---|---|---|---|
| greedy | 69.3% | 33 min | 28.5% | 0 |
| reactive | 69.1% | 33 min | 28.3% | 4 |
| ephemeris | 70.7% | 34 min | 28.1% | 0 |
| contact_aware | 69.4% | 33 min | 28.0% | 90 |

## 读法

1. **连通的星座里, 接触切换被星间中继吸收了。** Walker 场景里 RS 每小时换 12 次对端, 但只要它连着任何一颗算力星,
   就能经面内环和跨面链路到达全部 40 颗。结果回传几乎不等 (deliver gap 接近 0), 迁移中止 0 次。
   "单链路接触 7–8 min → 强迫迁移"这个推论在有 ISL 网格的星座里不成立, 要在论文里改口。
2. **剩下的差距来自地影, 而且大部分靠放置就能拿到。** greedy → ephemeris 把长任务达标从 95.9% 提到 99.3%,
   contact_aware 再多 0.6 个点。也就是说 3.4 个点里约 85% 是放置买到的, 运行中迁移只贡献约 15%。
   这和 orbitsim 几何分析的"星历放置基线能消掉大部分地影迁移"一致, 现在有了请求级的数。
3. **反应式迁移不如星历放置。** reactive 把影内解码压到 0.2%, 但达标只有 97.1%: 它先把请求放到即将进影的星,
   再花迁移搬走, 而且迁移目标不看未来。审稿人问"为什么不进影就搬", 这张表就是回答。
4. **簇间不连通时, 交付等的是下一次过境, 调度救不了。** S-SSO2 的 4 个簇互相从不进入 5000 km, RS 每小时只碰到
   一次算力簇。长任务交付 p90 长达 33 min, 约 30% 超时; 四种策略差距 < 2 个点, 因为簇内 4 星同时进影
   (orbitsim sow_events P1: 首尾时差 ≤ 100 s), 簇内迁移没有亮星可去。这类构型的瓶颈在拓扑, 不在调度。
5. **带宽不是瓶颈。** 10 Gbps 下 1.6 GB 的 KV 迁移要 1–2 s, 远短于分钟级的接触和地影。C2 (带宽争用) 要成立,
   链路得压到 0.1–0.5 Gbps 量级或加上数传背景流。

## 灵敏度 (Walker, 单种子)

| 变量 | greedy | ephemeris | contact_aware |
|---|---|---|---|
| 截止 3×, 6 请求/分钟 | 99.4% | 100% | 100% |
| 截止 2×, 45 请求/分钟 | 96.1% | 99.4% | 99.9% |
| 截止 1.5×, 45 请求/分钟 | 86.6% | 83.9% | 84.6% |
| stream 交付 (解码中不允许断联), 45/分钟 | 91.4% | 95.2% | 95.6% |

(长任务达标率。) 截止压到 1.5× 时队列压力主导, 星历放置只看单请求交付时间、不看对已驻留请求的拖慢, 反而输给 greedy。
这是下一版策略要补的: 把放置对同节点其他请求的外部性算进代价。

## 对论文叙事的含义

- 迁移动机不要写成"接触窗口短"。有 ISL 网格时它被中继吸收; 没有网格时迁移也无处可去。
- 能站住的是: (a) 星历放置作为强基线必须在表里; (b) 运行中迁移的增量在 0.5–1 个点量级, 要靠
  更紧的截止、更长的 agentic 会话或不可预知的断电才能放大; (c) 拓扑设计 (簇怎么排、要不要跨簇链路)
  对交付时延的影响远大于调度策略 (S-SSO2 p90 33 min vs Walker 5.5 min)。

## 局限

地影 = 固定限功, 无电池与热模型; 无 prefill 算力; 无链路重捕获时间; RS 端点不中继; 单日 (春分) 2 h;
策略参数 (margin 20 s / 10%) 未调优。

## 复现

```bash
# orbitsim: 重新生成轨迹 (可选, input/traces/ 里已有)
cd ../orbitsim && uv run python export_cosim.py && cp cosim_out/*.json ../satsim/input/traces/
# satsim: 跑实验并写回放
uv run satsim-cosim configs/cosim_coop_w53_v1.yaml --viz ../orbitsim/viz/public/playback
uv run satsim-cosim configs/cosim_coop_sso2_v1.yaml --viz ../orbitsim/viz/public/playback
# 灵敏度
uv run python scripts/cosim_sweep.py configs/cosim_coop_w53_v1.yaml slo.deadline_factor_long 1.5 2 3 --seeds 1
# 看回放
cd ../orbitsim/viz && npm run dev   # http://localhost:5288/play.html
```
